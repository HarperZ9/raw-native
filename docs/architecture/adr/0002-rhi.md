# ADR 0002: The render hardware interface

**Status:** Accepted for the interface and the D3D12, WebGPU and null backends.
Backend order and the shader language are **Proposed** (author decisions A1
and A5). **Date:** 2026-10-04.

## Context

In 0.5 the D3D12 and WebGPU backends each implemented the whole GPU frame:
buffer creation, upload, the six compute passes with their bindings, the
read-back and the unpacking. The pass list, the binding order and the buffer
sizes existed twice, and a third backend would have made three copies. Each
backend also placed its own synchronization: D3D12 issued a global UAV barrier
after every dispatch, WebGPU relied on pass boundaries.

The mature designs split this in two. wgpu puts a thin backend layer
(wgpu-hal) with no validation and no state tracking under a core that tracks
usage and inserts barriers. Unreal's RHI is one `FDynamicRHI` per API under
command lists, with barriers coming from the render dependency graph above it.
Godot's RenderingDevice sits under a graph that places barriers automatically
since 4.3. Sources are in [GAP-ANALYSIS.md](../GAP-ANALYSIS.md#sources).

## Decision

`raw/rhi/rhi.hpp` defines the interface; `src/rhi/<backend>/` implements it.

- **Object model:** `Device`, `CommandList`, buffers and compute pipelines as
  generational handles (`Handle<Tag>`: index and generation, generation 0
  never issued). A stale handle fails; it never aliases a new object.
- **Commands:** `upload`, `copyBuffer`, `dispatch`, `barrier`. Errors are kept
  by the command list and returned by `submitAndWait`, so recording calls have
  no return values to forget.
- **No hazard tracking in the RHI.** The frame graph declares every access and
  passes explicit `BufferBarrier{buffer, before, after}` records down. A
  backend maps them to its API: D3D12 turns an access change into a transition
  and a write between two storage accesses into a UAV barrier; WebGPU records
  nothing, because WebGPU orders passes itself.
- **Memory on D3D12:** one committed resource per buffer. Uniform buffers live
  in an UPLOAD heap and are written by the CPU; read-back buffers live in a
  READBACK heap; everything else lives in a DEFAULT heap. Barriers apply only
  to DEFAULT-heap buffers.
- **Pipelines take a binding layout,** generated from the WGSL declarations
  (`src/renderer/gpu/shaders/pass_layout.hpp`). D3D12 builds its root signature
  from it; WebGPU checks each dispatch against it.
- **Shader formats:** the device says which format it takes (WGSL or DXIL), and
  the renderer's shader library supplies that format. A build carries one.
- **Backend selection is at link time:** a build links exactly one backend
  (`rhi::device()` and `rhi::linkedBackend()` are defined once).
- **The D3D12 debug layer fails a submission** on any error message when
  `RAW_NATIVE_D3D12_DEBUG=1`. A deliberately dropped transition was caught this
  way while this ADR was written, which is the check's negative control.
- `kRhiVersion` is bumped when a backend or a caller must change.

## Consequences

- The pass setup exists once, in the renderer. A third backend implements
  roughly 300 lines of API mapping and nothing about the frame.
- WebGPU now waits for `OnSubmittedWorkDone` before a read-back is mapped,
  and D3D12 places per-resource barriers where it used to place a global one.
  Neither changes a byte of output; the identity matrix in the pull request
  shows it.
- The interface covers buffers and compute only. That is all the renderer
  uses, and adding methods before a caller exists would be guessing.

## What comes next, in order

1. Textures, texture views and samplers; graphics pipelines and render passes
   (needed for the PBR milestone).
2. Timestamp queries, so certificates report measured GPU time.
3. A surface and swapchain, with HDR output (scRGB FP16 by default, HDR10 as
   an option, following Microsoft's HDR guidance).
4. Suballocation through a GPU memory allocator (D3D12MA, VMA) once the
   dependency policy allows it ([ADR 0005](0005-dependency-policy.md)).
5. A validating layer between the renderer and the backends, wgpu-core style,
   enabled in debug and CI builds.
6. Backends in the order the author sets (A1). Proposed: Vulkan next, because
   it reaches Linux, Android and the Steam Deck with one backend; Metal after.

## Shader language (A5, Proposed)

The WGSL subset and the in-repo translator stay through the next milestone:
they cost no dependency and CI proves the HLSL matches. Textures and material
permutations will strain the subset. At that point the options are to grow the
translator, or to adopt Slang (Apache-2.0 with LLVM exception, Khronos-hosted
since November 2024, targets DXIL, SPIR-V, Metal and WGSL, with reflection).
The choice belongs with the dependency policy.

## Alternatives considered

- **Adopt an existing abstraction (wgpu-native, Dawn, bgfx, SDL3 GPU).** Each
  would replace this layer with a large dependency, and each owns its own
  synchronization, which the certificate path needs to see and control. Kept as
  a fallback if the in-house backends fall behind on platform reach.
- **Keep the RHI tracking state itself** (each backend remembers resource
  states). Simpler for callers, but it hides the barrier plan from the graph,
  which is the one place that can explain and test it.

## What would reverse it

If a backend needs knowledge of the frame to perform (for example render-pass
merging on tile GPUs), the graph must pass that down as data. If that grows
into the RHI re-deriving the frame, the split is wrong.
